# 既知の問題、クラッシュの仕組み、復旧

**2026-11-05 時点**の spacewar / Windows 11 22H2 基準構成を対象にする。プラットフォームの **0x101** フリーズと ADSP の **0x0A** 開始順クラッシュは別の障害。ノイズ表示、ドライバ開始失敗、システム無応答も別の観測として、何が起きたかを記録する。

## 1. BugCheck 0x101：プロセッサ間の相互ランデブー

**PROVEN な機構：** 採取したスタックでは2プロセッサが flush broadcast に伴うプロセッサ間ランデブーへ入り、どちらも完了しない。グラフィックス側の相手は任意のシステム活動なので、`qcdxkm7325` のスレッドだけを直列化しても防げない。組になる CPU は実行ごとに異なり、固定の2 CPU を無効にする案は対策として却下した。

**OPEN な根本欠陥：** 停止 CPU で割り込みの配送、CPU の受理、ハンドラ進行のどこが止まるかは未確定。通常のクラッシュダンプに有用なレジスタ文脈が残らない場合がある。CPU ごとの自己記録計測（GX74 の設計作業）はこの層を区別する目的で、ここで配布する完成済み修正ではない。

手動 GPU 有効化、GPU 有効でのブート、稀に GPU 無効でもダンプ書き出しなど重いブート初期処理で観測している。表示の有効化自体が再描画など別の活動を誘発するため、静かな時間を選んでも安全は保証できない。記録上はプロセッサのアイドルを有効にする方が安全で、アイドル無効化は確立した回避策ではない。

### 運用上の緩和策

1. GPU はブート時無効とし、自動有効化・自動再試行タスクを避ける。
2. 目的を決めた短い実験だけ手動有効化し、できればサインイン画面の静かな時間を選ぶ。サインイン後に試すなら背後の活動を減らすが、どちらも根治ではない。
3. 必要な証拠を速やかに採取して無効化する。ノイズ状態のパイプラインを回し続けると発熱する。
4. 有効化後の再起動前には毎回 ConfigFlags=1 を確認し、後片付け未完なら次の Windows 起動前にオフライン修復する。
5. 実験設計では不要な flush のバーストや有効化の往復を減らす。ただし確定した修正とは説明しない。

これはタッチ・Wi-Fi・Bluetooth の基準構成を守り、障害に遭遇する機会を減らす対策。今後フリーズしない証明にも、DSI FIFO underflow が CPU デッドロックを起こす証拠にもならない。

## 2. ConfigFlags の罠：実行時有効化が次のブートにも残る

`pnputil /enable-device` はグラフィックスの無効フラグを永続的に解除し、**ConfigFlags=0** にしうる。実行時有効化はブート設定を変えないという旧理解は、オフラインハイブの実測で否定された。無効化前にクラッシュすると次のブートでも GPU が開始する。連続ブート凍結は新しいパッチの退行ではなく、前回有効化の残存状態かもしれない。

現行の `gpu_now` は有効化して5分間状態を記録するだけで、無効化、ConfigFlags 復元、クラッシュ復旧を行わない。最後に “survived” と記録されても、次のブートが安全とは限らない。

### 正常な動作中セッションで毎回確認する

管理者プロンプトでデバイスを無効化してから照会する。コマンドの戻り値だけで永続化を推測しない。

```bat
pnputil /disable-device "ACPI\VEN_QCOM&DEV_0A36&SUBSYS_IDP07325&REV_0118\0"
reg query "HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\VEN_QCOM&DEV_0A36&SUBSYS_IDP07325&REV_0118\0" /v ConfigFlags
```

期待値は **REG_DWORD 0x1** とデバイスの無効状態。1でなければ安全な設定と思い込んで再起動しない。不安定なライブセッションを繰り返さず、必要ならオフライン復旧を使う。

### オフライン復旧例

電話の Windows を停止し、ガジェットモードでボリュームを公開する。例の `W:` は照合済みの電話 Windows ボリュームだけを指す。保守環境の管理者プロンプトで実行し、バックアップは非公開でリポジトリ外に保管する。

```bat
copy W:\Windows\System32\config\SYSTEM W:\Windows\System32\config\SYSTEM.pre-recovery
reg load HKLM\PhoneSystem W:\Windows\System32\config\SYSTEM
reg query HKLM\PhoneSystem\Select
```

`Select\Default` を使って次回通常起動のコントロールセットを特定し、`Current`／`LastKnownGood` と比較する。実証済み構成は **ControlSet001**。以下はその選択を確認済みの場合の例で、違うなら実際のセットに置換する。編集前にも値を照会する。

```bat
reg query "HKLM\PhoneSystem\ControlSet001\Enum\ACPI\VEN_QCOM&DEV_0A36&SUBSYS_IDP07325&REV_0118\0" /v ConfigFlags
reg add "HKLM\PhoneSystem\ControlSet001\Enum\ACPI\VEN_QCOM&DEV_0A36&SUBSYS_IDP07325&REV_0118\0" /v ConfigFlags /t REG_DWORD /d 1 /f
reg query "HKLM\PhoneSystem\ControlSet001\Enum\ACPI\VEN_QCOM&DEV_0A36&SUBSYS_IDP07325&REV_0118\0" /v ConfigFlags
reg unload HKLM\PhoneSystem
```

各操作の成功を確認し、同じハイブを再ロードして同じ値をもう一度照会し、アンロードしてから安全に取り外す。2回目の読み取りはアンロード後の永続状態の確認で、flush 前のレジストリエディタ表示だけでは足りない。以前の復旧バックアップを上書きしたり、別端末・別構成の SYSTEM ハイブを丸ごとコピーしたりしない。ここでの基準値は厳密に1。別環境で他の構成ビットがあるなら、元値をバックアップに残して確認する。

ADSP のブート開始も有効にした場合は、実際に列挙された ADSP インスタンスを特定し、同じ確認済みセットで無効の基準へ戻す。グラフィックスのパスを代用したり、ADSP のインスタンス末尾を創作したりしない。

## 3. ADSP ブートクラッシュ：BugCheck 0x0A

**PROVEN な静的所有関係：** `qcsubsys7325.sys` は呼び出し RVA **0x4B214**（戻り **0x4B218**）で、埋め込み Qualcomm MSM Interface（QMI）ミューテックス **image+0x76568** を待つ。渡しているのはオブジェクトのアドレスで、NULL ではない。静的領域は initializer RVA **0x48210** 実行までゼロのまま。初期化連鎖は SSDD 登録 callback **0xB3C50 → 0x4B6C8 → 0x48210** で、最初の登録時に初期化する。SSDD は **Qualcomm Subsystem Dependency Device / QCOM0A20**。QSM は別の **Qualcomm Service Manager Device / QCOM0A1E** で、このミューテックスを初期化しない。

未初期化 dispatcher object の待機は、オブジェクト自体のアドレスが有効でも内部 wait-list の NULL リンクを参照しうる。静的報告だけでは戻りアドレスから故障したカーネル内フィールドを確定できなかったが、その後の実行時／ブート対照試験で開始順序の結論が補強された。NULL のミューテックスポインタ、ファームウェア探索失敗、QSM を有効にすればよいという話へ置き換えない。

**2026-11-04 の PROVEN な実験：** SSDD が既に開始した通常ブートの後、サインイン後に ADSP を手動有効化すると Status=OK、問題コードなしで Peripheral Image Loader（PIL）経由のファームウェア開始まで通る。一方ブート中の開始では**バイト同一の呼び出し位置で 0x0A** を再現した。判別条件は開始**順序**であり、SSDD の ConfigFlags=0 だけでは不十分。運用上は ADSP をブート無効にし、必要なら SSDD 準備後に実行時有効化する。

パックには `qcadsp7325.mbn` があり、Audio 拡張が自身の DriverStore へ導入して `ADSP\ImagePath` を設定する。本当にイメージがなければ検査付きのローダー失敗経路となり、この未初期化 QMI ミューテックスとは別。Wi-Fi 用 WPSS が動いても ADSP 全経路の準備完了は示せない。ADSP は audio／sensor の保護ドメインと追加の service-registry／QMI 活動を持ち、調べた WPSS 構成の保護ドメインは0。元のクラッシュの上位呼び出し元全体は復元できていないので、その差は根拠のある説明であって完全な復元スタックではない。

実行時 ADSP 開始は、バッテリー、内蔵音声、センサーの動作を示さない。PMIC／電池チェーンは ADSP なしのブートで形成され、全デバイスが開始しても `Win32_Battery` は空のまま。これらは実行時停止・再開始を拒否した。ブート初期から正しい順序で ADSP が存在すれば変わるかは未検証。[サブシステム詳細](subsystems.ja.md)を参照。

## 4. ダンプと証拠の保存

watchdog や強いフリーズでは通常の bugcheck dump なしで Android に戻ることがあり、その後のダンプ書き出し用ブートも凍結しうる。v3.8 採取セッションと後の書き出し試行では新しいダンプが残らず、以前の ADSP 0x0A ダンプが残った。クラッシュコードを結びつける前に、必ず時刻と実セッションを照合する。

次の採取で上書きする前に、残ったプローブ結果とログを保存する。DscProbe は段階的に flush するが、in-progress は途中の結果で、完成ファイルも前回ブートのものかもしれない。最後の操作が enable／採取／disable／reboot のどれか、ConfigFlags の後片付けが済んだか、表示が黒／ノイズ／画像のどれかを記録する。共有前に所有者識別情報を取り除き、生ダンプとログはリポジトリに入れない。

## 5. その他の復旧上の境界

- 通常ブートは KD オフ。設定済みデバッグトランスポートがホスト不在で待つ問題は 0x101 とは別。
- DriverStore 保護ファイルをライブ上書きしない。デバイス無効化でも安全にはならず、整合する再署名ファイルと検証済みパッケージでオフライン／ガジェット保守する。
- ブート中のタッチ用生電源投票を追加しない。過去に現役の電源管理と競合し SOC_CRITICAL_DEVICE_REMOVED になった。確立した mux 自動復元を使う。
- Android の `/dev/mem` から表示 MMIO を総当たりしない。サイレントリセット2回で中止済み。アドレスがマップ済みでも給電・クロック有効とは限らない。
- GPU の無効化／再有効化がパネル全電源断を行うとは未証明。コントローラ／FIFO reset、PHY 準備、パネル init／PPS、物理 reset／電源は別範囲で、skip flag と callback にも依存する。

[導入ガイド](install.ja.md)に安全な基準構成を、[表示調査](display-investigation.ja.md)にデコーダ全復旧と FIFO 因果関係が未確定な理由を記す。
