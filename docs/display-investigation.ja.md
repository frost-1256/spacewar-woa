# 表示と DSC の調査記録

**2026-11-05 時点**、Nothing Phone (1) / spacewar、Windows 11 22H2、`qcdxkm7325.sys` **dsc2** の記録。表示は**正常動作していない**。永続的なノイズの説明としてレジスタ設定値の監査は完了し、残る調査はフレーミング、順序・タイミング、DSI エラー領域に移っている。非公開の作業ノートがなくても、その境界と根拠を理解できるようにまとめる。

## 1. 用語と確度

Display Stream Compression（DSC）はハードウェアで画素を圧縮し、Picture Parameter Set（PPS）はパネル側デコーダに復号条件を伝える。Display Serial Interface（DSI）ホストはそのストリームをパケット化して直列転送する。表示パイプラインにはレイヤミキサ（LM）、pingpong ブロック（PP）、制御ブロック（CTL）、DSC エンコーダ、インターフェースブロック（INTF）がある。モード設定の成功や走査カウンタの進行だけでは、圧縮データの正しい配送は示せない。

- **PROVEN（確定）：** 実機での観測、または同定したソース・逆アセンブル・バイト比較による直接の証拠。どの種類の証拠かも記す。
- **EXCLUDED（除外）：** 特定の説明に反証がある、または切り分け実験で症状が変わらなかったもの。除外の範囲を守る。
- **INFERENCE（推論）：** 証拠と整合するが、直接実証していない説明。
- **OPEN（未確定）：** 現在の証拠では判定できないもの。
- **PLANNED（計画）：** 解析・提案段階で、実装や試験をしていないもの。

明示的にファイルオフセットと書かない限り、ドライバ位置は同定済み原本グラフィックスイメージからの **RVA**。物理 MMIO アドレスではない。パッチのオフセットとバイト列は保護した[パッチ表](../patches/README.ja.md)を正本とする。読み取り専用の採取はワイヤ上の記録ではなく、各コマンドのパネル受理を証明しない。

## 2. パネル、見える症状、基準状態

| 項目 | 記録された構成 |
|---|---|
| パネル／コントローラ | Raydium RM692E5 を使う Visionox パネル |
| 有効解像度／リンク | 1080×2400、DSI コマンドモード |
| 圧縮 | DSC 1.1、SCR revision 0 |
| 成分深度／圧縮レート | 10 bits/component、8 bits/pixel |
| スライス／パケット | 540×20、2 slices/packet、全幅1行に2スライス |
| 予測／変換 | Block prediction と RGB conversion 有効、native 4:2:2/4:2:0 なし |
| Windows ドライバ | dsc2 = capw + dsc1 + CTRL2 スライス幅修正 |
| 安全な基準 | ブート時 GPU 無効、短時間の手動実行時テスト |

**PROVEN：** ドライバは開始してパネルを駆動し、走査線の活動も進むが、圧縮出力は構造のあるノイズになる。黒画面は別の観測で、転送自体が始まっていない場合があり、ノイズと一括りにしない。写真計測ではノイズが行0〜約580、継ぎ目が x=541 付近、左スライス列に20行周期、右に60行周期、行164付近から繰り返しが見られた。スライス境界との整合はフレーミング不良の候補を制約するが、特定のバイト順や詰め物のバグまでは示さない。

有効なノイズ状態では発熱するため、実験後は速やかに無効化する。サインイン画面の静かな条件は背後の活動を減らすが、別件の 0x101 ランデブーフリーズは防ぎきれない。[既知の問題](known-issues.ja.md)、特に永続的な ConfigFlags の確認に従う。

「設定値の線は終了」は、異なる OS の全レジスタが一致するという意味でも、ワイヤ上のバイトを検証済みという意味でもない。想定した有効時設定の誤り・欠落の説明を監査し終えたという意味。転送の時間的挙動や圧縮バイト列のフレーミングは別の問いとして残る。

### パケタイザの計算

幅1080、スライス幅540、圧縮8 bits/pixel から、2 slices/interface、540 bytes/slice、1080 bytes/line と bytes/packet、1 packet/line、行末詰め物は `1080 % 3 = 0` となる。DCS memory-write の1バイトを加え、ワードカウントは **1081**。10 bits/component は PPS／エンコーダ条件で、この圧縮バイト数の式には影響しない。

```text
CTRL (VC0)      = 0x3901
CTRL2 (VC0)     = 540 = 0x021C
STREAM0_CTRL    = (1081 << 16) | 0x39 = 0x04390039
TOTAL wide bus  = (2400 << 16) | ceil(1080 / 6) = 0x096000B4
TOTAL narrow    = (2400 << 16) | ceil(1080 / 3) = 0x09600168
DCS_CMD_CTRL    = 0x00013C2C  (start 0x2C, continue 0x3C, insertion enabled)
```

CONFIG2 の bit0 は widebus、対象世代の bit12 は圧縮64-bit入力、bit4 は DATA_HCTL_EN。コマンドモードの有効化では他の状態を保持する。ベンダー更新は普遍的な全レジスタ定数ではなく、観測された保持値を前提に0x1111となる。bit8 の意味はこのソース監査では未確定。実験では普遍的な定数を仮定せず、関係するタプル全体を試した。

## 5. 正常メインラインの参照と実値比較

2026-11-05 の postmarketOS netboot 採取はメインライン **7.2.9-sc7280** を使い、fbcon／デバッグシェルの正常表示中に行った。一般的なユーザー空間のフルブート完了までは示していない。割り当ては LM_0、PP_0、CTL_0、DSC_0 各1個、出力は INTF_1／DSI-1。Windows も同じ形のパイプラインで、Fairphone 5 の「2ミキサ＋マージを1個の DSC へ入れる」失敗例とは構成が違う。

| 正常メインラインの計測項目 | 値 |
|---|---|
| モード | 1080×2400 @ 120 Hz |
| 水平タイミング | 1080 / 1106 / 1145 / 1181 |
| 垂直タイミング | 2400 / 2416 / 2437 / 2453 |
| 非圧縮換算のモードクロック | 347639 kHz |
| DSI bit clock / PLL VCO | 687,035,888 Hz |
| Byte / byte-interface clock | 85,879,486 / 42,939,743 Hz |
| 実 INTF pixel clock | 114,505,982 Hz |

モードクロックと圧縮領域の実 INTF pixel clock は同じではない。これは正常な **120 Hz** メインラインの実測で、Windows の実測値や必須定数ではなく、将来の無圧縮 **60 Hz** 経路でも維持できることの証明でもない。

### 相違する値 — 採取表と新しい Windows エラー実測

物理参照ブロックは DSC_0 `0x0AE81000`、DSI0 `0x0AE94000`、INTF_1 `0x0AE36000`、CTL_0 `0x0AE16000`。DscProbe は表示ドライバが既に持つ仮想 MMIO マッピングを使う。物理アドレスをドライバ RVA として使わない。Windows 設定値は複数採取とタプル実験から成り、表全体が同時刻の OS 間トレースではない。

一致する実値も経路を制約する。DSC 制御 +0xF00=0、+0xF04=0x00020001、+0xF08=0x0002C688、DCS_CMD_CTRL=0x00013C2C、CTRL2=540、INTF mux=0x000F0000、CTL_TOP=0xF0020000、DSC_ACTIVE=1、INTF_ACTIVE=2。スタック間のパケット化差だけを理由に、ベンダーと一致する Windows 定数を置換する根拠はない。

メインライン生値は、後の DEVMEM 有効カーネルで mmap により採取できた。採取資料の前半にある「取得不可」は最初のカーネルに限った記述。これは Android の無制限な `/dev/mem` 読み取りが安全という意味ではない。そちらではクロック停止ブロックへのアクセスが疑われるサイレントリセットを2回起こし、経路を中止している。DscProbe でも表示の給電・クロック有効が前提で、マッピングの存在だけでは電源上の安全性を示せない。

## 6. 最新の観測：HS レーン FIFO underflow 群

**PROVEN な観測：** 2026-11-05、DscProbe **v3.8**、dsc2、DSC **オン**で FIFO_STATUS **0x99991290** を採取した。正常メインラインは **0x11111210**。Windows には bits19/23/27/31、つまり HS レーン FIFO underflow の **0x88880000** 群があり、メインラインにはこの群がない。下位ビットにも差があるため、全ワード差が underflow だけだとはせず、対象群を明示する。

同じ Windows 採取で `pi+0x1A18=1`、固定 bit-clock override `cfg+0x1BC=0`（自動計算経路が有効）、導出 bytes フィールド1080、スライス数2、DF_CTRL=0x095C0004、CTRL2=540、CONFIG2=0x1111 を再確認した。内部名 bytes-in-slice のフィールドにはこの経路で導出値1080が入る。ベンダー式の「物理スライス1個あたり540圧縮バイト」と、ソフトウェア内部フィールド名を混同しない。

### 静的エラー監査との接点

- Windows は DSI エラーを**読んで分類する**。getter RVA `0x157BF0`、選択的 Write-1-to-Clear（W1C）helper `0x157D88`、通常 query `0x124570` selector 6 が存在する。
- FIFO bits19/23/27/31 は両 classifier と clear の逆変換にない。mask/unmask helper も対応 mask bits26/27/29/30 を操作しない。ただし未操作だから現在必ずマスク／アンマスクとは断定できない。
- 診断ラッパは戻り値から HS レーン **overflow** の詳細も落とす。overflow と underflow は別の群。
- 通常 query は対象を計算・クリアした後、上位 summary に Phase-Locked Loop（PLL）unlock だけを残す。非 PLL の FIFO／timeout／ACK／PHY 詳細が失われるので、事後の0は履歴が正常だった証明にならない。
- コマンド転送失敗の復旧は存在するが、DSI コントローラとコマンド FIFO のリセットまで。FIFO／timeout を契機にパネル init と PPS 再送まで届く復旧連鎖は確認できていない。

監査したアドレス構築は `M=Q[image+0x227558]`、controller 0 は `M+0x94000`、controller 1 は `M+0x96000`。生のエラー集合は FIFO +0x00C、ACK +0x068、PHY +0x0B4、timeout +0x0C0、mask +0x10C、interrupt +0x110、clock/status +0x120 で、v3.8 はこの集合を含む。FIFO は通常状態と sticky error が混在し、特に INT_CTRL は enable／W1C 混在なので無差別な書き戻しは危険。

### 公開事例と断定できない範囲

公開された [OnePlus 7T Pro の転送エラー記録](https://github.com/Sr-0w/hotdog-linux-bringup/blob/main/docs/evidence/2026-08-17-dsi-dsc-transport-errors.md)にも、全レーンの `0x88880000` と DSC の破綻が併発する。そちらはパネル全再初期化で回復し、広いエラー群へのコントローラリセット追加は悪化を招いた。調査対象としての根拠にはなるが、リセット修正を移植する根拠ではない。そちらは正常表示から劣化する間欠型で、spacewar は有効化直後からノイズという違いがある。

**OPEN：** 「underflow がこのノイズの原因」とも「Windows の正常状態」とも確定していない。残存状態1枚では、最初の原因がラッチされたのか、別の障害の結果か、害のない遷移時の痕跡かを分離できず、CPU ランデブーフリーズとの関係も示せない。採取セッションは GPU を無効化できないまま後でリセットし、オフラインで ConfigFlags=0 を確認して1へ戻した。このセッションと後続の書き出し試行で新しいダンプは残らず、古いダンプから今回の事象は説明できない。

### 切り分け実験 — まだ未実施

| 実験 | 採取・対照 | 分かること |
|---|---|---|
| 有効化をまたぐ時系列 | 最初に給電された時点、最初のフレーム、後のノイズで FIFO／error／mask を採取し順序と reset 境界を記録 | 対象群がノイズより前・同時・後のどこで立つか |
| DSC オフビルドとの比較 | ホストとパネルの無圧縮設定を検証した上で同じ集合を採取 | 圧縮経路固有か。壊れたオフ構成では判定不可 |
| クリア後監視 | 独立にレビューした限定的 W1C 実験で初期値保存後に再セットを観測 | sticky な履歴か継続発生か。証拠変更前に採取する |

DscProbe は**読み取り専用**を維持する。クリア後監視やテストパターン注入には別の実験コードが必要で、プローブはその機能を持たない。ドライバ自身の clear 前に記録すれば失われる詳細を保持できるが、これは提案であって適用済みパッチではない。新たな割り込み源の unmask には対応表・clear 順序・頻度制御が必要で、単なる観測変更とは扱えない。

## 7. 有効化の順序とパネル資料の限界

Windows の静的順序は calculator／PPS 生成 → DSI／パネル bring-up callback → PPS 送信（`0x10FA6C`）→ ホスト encoder leaf／共通書き込み（`0xDD578`）。先行 CTL flush は早すぎる初回フレームの証明ではない。保存された経路では CTL_START を発行しない。最初のフレーム開始と最終ハードウェアラッチの時刻は、この静的経路だけでは未確定。

正常な[メインライン Visionox ドライバ](https://linux.googlesource.com/linux/kernel/git/torvalds/linux/+/refs/heads/master/drivers/gpu/drm/panel/panel-visionox-rm692e5.c)の prepare 最後は、表示オンまでの初期化、PPS（DT=0x0A）、compression-mode enable（DT=0x07）、28 ms 待機。採取した downstream の on-command 表は106件／955バイトで PPS も圧縮モードパケットも含まないが、PPS は別に生成される。downstream ソース検索で明示的な0x07送信が見つからなかったことは、その調査範囲の結果で、framework／host／firmware の全経路が送らない証明ではない。

v26/v27 の PCFG 挿入では既に0x07を両順序で試して復号が直らなかった。ただし完全な順序再現は別の実験。表示オン後の PPS → 0x07 が**最後の**コマンドになり、待機を入れ、後から自動 PPS が来ない条件が必要になる。候補フックは通常 PPS 呼び出し直後の **RVA 0x10FA70**。計画段階の実験であり、0x07 欠落が原因だと主張するものではない。

**2026-11-05 の資料検索結果：** 英語・中国語、PDF、文書リポジトリ、コードを含む12クエリで、RM692E5 の display driver IC（DDIC）データシート／レジスタ仕様書は公開資料から見つからなかった。公開モジュール仕様は電気・機械・ピン情報にとどまり、必要なコマンドの意味を持たない。メインライン Visionox と Fairphone／BOE の初期化列は参照にはなるが、注釈付きレジスタマニュアルではない。同族 RM690B0 の公開文書は FE によるページ選択という共通構造を裏付けるだけで、RM692E5 の D1／D2／B4 の DSC 制御は定義しない。これは日付付きの否定的な検索結果で、将来も文書が公開されないことの証明ではない。

したがってパネル側 DSC オフ値は実験で決める必要がある。`FE D1 / B4 01` と `FE D2` の PPS ミラーを類推だけで確定した解除手順へ変換できない。特に **B4 01→00 は確立したパッチではなく**、別解像度の BOE 列から本パネルの DSC パラメータを流用してもいけない。

## 8. DSC オフ経路 — 条件付きで可能、未実装

目的は、切り分け／フォールバック用の安定した無圧縮 **1080×2400、60 Hz** 表示。静的解析は非 DSC の部分経路を証明したが、端から端までの成功は未証明。主フラグは **panel-info `pi+0x1A18`**。DSI の **`cfg+0x1A08`** は `cfg=pi+0x10` なので同じフィールド。caps サブ構造 +0x0C は計算・ハードウェア経路の選択で、別の主スイッチではない。最初にこのフラグを設定する宣言的 XML／レジストリ入口は未同定。

flag=0 でエンコーダ設定を迂回し、既存経路で INTF 圧縮入力／widebus を解除し、生成 PPS を抑止できる。ただしフラグだけの実験を無意味にする穴が2つある。コマンド生成側がレコード生成 helper を飛ばして WC が **0** のままになり、packetizer は enable=0 で圧縮レジスタ書き込みを飛ばして明示的な圧縮解除をしない。

### ホスト側試作 — 提案のみ

起点は **原本へ累積 dsc1 を適用したもの**（capw を含む）にする。dsc2 だと固定 CTRL2=540 がオフ経路にも残る。以下は可否解析からの命令候補で、**patches.json の配布パッチ仕様ではない**。ここでバイト符号化、署名、配備は行っていない。

| RVA | 既存命令 | 試作案 | 目的 |
|---|---|---|---|
| 0x11180C | `ldr w8,[x20,#0x1a08]` | `str wzr,[x24]` | 既にアドレス化された主フラグを0にする |
| 0x111810 | `cbz w8,#0x111858` | `b #0x111858` | DSC 比率／表の経路を飛ばす |
| 0x1269CC | `ldr w9,[sp,#0x58]` | `mov w9,#0xCA9` | 1080幅 RGB888 専用 WC=3241 |
| 0x126B40 | `cbz w11,#0x126BA0` | `nop` | ゼロのレコードでも圧縮レジスタ設定へ進める |

合計は**ホスト4命令**で、別途パネル・モード・クロック作業が要る。試作ではソフトウェア WC が0のままハードウェア WC だけ3241になる場合がある。継続版は builder 側を補完するべきで、この固定幅試作は任意幅、ROI、DSC 再有効化を扱えない。設定呼び出しを迂回するだけでは既存エンコーダの停止を保証できず、teardown と active／enable レジスタも検証する。

| 提案する raw RGB888 経路での観測条件 | 値・要件 |
|---|---|
| 主フラグ／object DSC enable | pi+0x1A18=0、object+0x36C=0 |
| STREAM0_CTRL / TOTAL | 0x0CA90039 / 0x09600438 |
| DSI 圧縮 | 原本+dsc1 経路で CTRL=0x3900（bit0解除）、CTRL2/CTRL3=0 |
| Widebus／圧縮入力 | DSI MDP_CTRL2 bit20解除、対象 INTF CONFIG2 bit0/bit12解除 |
| ホスト encoder／CTL | DSC_CFG bit0解除、DSC_ACTIVE=0、正しい flush と raw 入力 binding |
| クロック／パネル | lane／INTF 実クロック受理、PLL lock、パネルが本当に無圧縮 RGB888、整合する60 Hz |

通常 raw 経路は16／18／24 bppを受理し30 bppを拒否するため、10-bpc DSC を理由に raw RGB101010 を要求しない。RGB888 の有効画素ペイロードだけで `1080×2400×60×24 = 3,732,480,000 bit/s`、4レーンなら **933,120,000 bit/s/lane** が必要で、パケット overhead、遷移、コマンド転送窓は別途加わる。同リフレッシュの圧縮8 bppに対して3倍、DSC 120 Hzと比較しても1.5倍なので、低リフレッシュ化だけで必要帯域が減るとは限らない。

最新の DSC オン採取では override=0 で自動クロック計算が使えるが、将来のオフビルドの要求値・プロバイダの受理・実クロックを証明しない。INTF **約229 MHz** は目安であり確立した設定値ではない。パネルの無圧縮コマンドモード受信、画素形式、解除コマンドとタイミングは OPEN。PPS が止まってもデコーダ解除の証明にはならない。FE 群の維持・除去や標準圧縮解除などの候補を、推測した意味ではなく読み戻しと表示で判定する必要がある。

成功にはソフト状態、ホスト実レジスタ、パネル設定の一致に加え、単色、RGB 順序、縦横線、全画面格子、階調、コールドブート後の再現性を含む正しく安定した全画面表示が必要。resume と追加モード設定はその後の検証になる。不完全な DSC オフ構成のノイズや黒画面では、圧縮／フレーミング障害を除外できない。

## 9. 段階的な打ち手と観測の限界

1. **DSC オフ実験：** 解析済みホスト候補とパネル・クロック実験を実装し、まず有効な raw 基準表示を作る。
2. **PPS→圧縮モードの最終順序再現：** 通常 PPS の直後でフックし、enable、28 ms待機、後続送信なしを作り、正常メインライン順序と比較する。
3. **テストパターン注入の二分探索：** 発生器が DSC の前後どちらか、コマンドモード対応はどうかを確定してから、INTF と DSI の注入点を既知信号で比較する。下流の無圧縮パターンが、DSC を期待するパネルに適した入力とは限らない。
4. **表示専用 Windows ドライバは最後の手段：** 切り分けでバイナリから必要箇所を変更できないと分かった場合に、公開実装からソフトウェア描画の表示経路を作る。3D 加速なしの月単位の作業で、既存の代替ドライバではない。

CPU ごとの自己記録計測（設計名 GX74）は別の安定性調査で、ランデブー中の割り込み配送、CPU 受理、ハンドラ進行を分ける目的がある。それ自体でフレーミングは直らない。相方が任意のシステム活動なので、ドライバ内直列化では防げない。flush のバースト抑制や静かな開始時刻の選択は緩和策の検討で、確定した根本修正ではない。

既知入力の写真は stride／スライス順／詰め物を制約できる。パネルの graphics memory 読み戻しを実装しても、得られるのは**復号後の画素**で、ハードウェア生成の圧縮ストリームではない。現構成に圧縮バイト列の直接観測手段はなく、未給電ブロックへの MMIO 総当たりも代替にはならない。このリポジトリにはパターン書き込み、GRAM 読み取り、DSC オフビルド、表示専用ドライバを含めていない。
